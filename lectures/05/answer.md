### 検索だけを実行して見つかったページと、その本文で確認できたこと

`uv run python -m app.retrieval "LoRA QLoRA 違い"` を実行した。

検索結果は、第2回のp.52、p.51、p.60、p.47、p.61の順だった。
p.52にはLoRAの元の重みを固定して小さな行列A・Bを学習する仕組みと、QLoRAで元の重みを4bitに量子化する説明があり、今回の質問に必要な情報がそろっていた。
p.51も補足として有用だったが、p.60、p.47、p.61は今回の質問への回答には必須ではなかった。

### `--trace`で見えたツール呼び出し

### 取得した情報が足りなかった例、取得できたのに回答へ使えなかった例

今回の質問では、4方式すべてで必要な根拠を取得し、ある程度正しい回答が得られた。
ただし、全文投入では資料に4bit量子化の説明があるにもかかわらず、回答では具体的なビット数が省略された。Graphでは行列A・Bの積で重みの変化分を表す仕組みについて、やや不正確な表現があった。

### 今回の用途に採用したい方式と、その理由・比較条件の限界

今回の質問には基本RAG（ベクトル検索）を採用したい。
全文投入と比較して、入力トークン数は約97.4%、生成API推定費用は約95.9%削減された。4方式の中で回答時間も最短だった。
Treeは正しいページに到達できたが、探索に4回のツール呼び出しが必要だった。Graphも正しく回答できたが、今回の質問では基本RAGに対する明確な改善は見られなかった。
ただし、対象資料の範囲が異なり、各方式1回ずつの測定であるため、方式全体の優劣は断定できない。また、生成API推定費用には埋め込みや索引構築の費用が含まれない。

### 気づき・疑問

検索で関連するページを多く取得することが、必ずしも回答精度の向上につながるわけではないと分かった。
今回の質問では、基本RAGの上位2ページだけで必要な情報がそろっていたため、検索件数を5件から2件へ減らすことで、回答精度を維持しながらトークン数や費用を削減できる可能性がある。
一方、複数ページに根拠が分散する質問では、検索件数を減らすことで必要な情報を取りこぼす可能性もあるため、追加の検証が必要だと考えた。
